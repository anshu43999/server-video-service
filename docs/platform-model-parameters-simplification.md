# 模型参数分层简化方案（admin-web 参数档案）

> 文档类型：领域设计方案 / 需求评审稿
> 对应基线：服务端与管理后台需求基线（PRODUCT_REQUIREMENTS.md）
> 关联权威文档：[平台统一模型参数](platform-model-parameters.md)（2026-11-16，M196 固化）
> 文档状态：待需求评审，不改变现有参数下发协议、发布流程与数据库
> 适用范围：服务端 `admin-web` 平台参数档案界面（`ParametersDialog.vue`）
> 编写日期：2026-11-20
> 本方案明确不做：按设备 / 场景自动计算参数（经确认本轮不做，且业务判定阈值须保持设备无关、跨设备一致）。

## 0. 背景与问题

用户反馈：平台模型参数档案要配置的项太多，是否有必要让用户配置那么多参数。

核对现状（`admin-web/src/features/models/ParametersDialog.vue` 与 `app/model_parameters.py`）：

- **检测基础参数** 3 项：识别置信度、IoU、最大检测结果；
- **每条类别规则** 展开后含：启用开关、业务名称、事件编码、严重度，再加
  - 拍照识别：图片告警置信度、图片冷却时间；
  - 相机巡检：视频告警置信度、最少连续帧、最少停留时间、视频冷却时间。

即单条标签最多需面对约 10 个输入项，一个多类别模型的配置面迅速膨胀。但其中多数项有合理工程默认、且非每次都需调整。

## 1. 目标

在**不改变参数下发协议、发布/CAS 流程、审计与数据库**的前提下，减少用户常规配置时实际需要面对的字段数量：

1. 区分“必须人工决定的业务项”与“有默认值的工程项”；
2. 默认只展示业务项，工程项收入“高级（可选）”折叠区，不填即用默认；
3. 保持所有现有校验与语义不变（尤其“告警置信度不得低于检测置信度”）。

## 2. 关键约束（不可触碰）

[平台统一模型参数](platform-model-parameters.md) 于 2026-11-16 刚统一固化（M196），以下一律不改：

- 参数身份 `modelId + modelVersion + platform`、草稿 / `publishedRevision` / `hasUnpublishedChanges` 语义；
- `publish` 的 `expectedRevision` / `expectedPublishedRevision` 双 CAS 与 409 冲突、审计 `PUBLISHED` 快照；
- 下发 JSON 的 `schemaVersion: 2` 结构与 legacy 兼容分支（`app/model_parameters.py` 的 `_normalize_profile`）；
- 服务端默认值来源 `default_profile`（置信度 0.35、IoU 0.45、maxDetections 100、冷却 60000ms 等）；
- App 侧只读消费，`ModelParameterProfile` 的回退逻辑（`cameraParameters()` / `imageParameters()` 在缺省时回退通用值）。

**本方案只改 admin-web 的“展示哪些字段、如何用默认值预填”，不改协议与存储。** 因此定级为界面改造（L1，涉及少量校验前移时 L2），不是 L3。

## 3. 分层设计

### 3.1 字段分层

| 层 | 字段 | 展示 | 理由 |
|---|---|---|---|
| 业务基线（默认展示） | 类别启用开关、业务名称、事件编码、严重度、告警置信度（一个通用值） | 始终可见 | 决定“算不算一次告警”，必须人工决定 |
| 工程高级（折叠，可选） | IoU、最大检测结果、最少连续帧、最少停留时间、冷却时间、拍照/相机分别覆盖 | 默认折叠，默认值兜底 | 有合理默认，非每次调整 |

- “告警置信度”在基线层只暴露**一个通用值**；用户若需为拍照与相机分别设定，再在高级区展开“分别覆盖”。这与 `ModelParameterProfile` 现有回退逻辑一致：image/camera 不单独设时回退通用值。
- 检测层的 IoU、maxDetections 移入高级区，用 `default_profile` 的值预填。

### 3.2 默认值来源

默认值继续来自服务端 `default_profile`，**不在前端另造一套默认**，避免前后端默认漂移。前端“高级”区未展开 / 未修改时，提交的就是服务端给出的草稿原值。

### 3.3 校验不变

`ParametersDialog.vue` 现有 `validate()` 的两条校验保持：

1. 事件编码格式、业务名称非空；
2. **启用规则的告警置信度不得低于检测置信度**（`rule.image/camera.minimumConfidence >= detection.confidenceThreshold`）。

折叠不等于跳过校验：高级区即使折叠，提交前仍对其中的值执行现有校验；若默认值已满足校验，用户无需展开即可保存发布。

## 4. 明确不做：按设备 / 场景自动计算

经确认本轮不做参数自适应。理由与边界（供后续评审留档）：

- **业务判定阈值（置信度、IoU、连续帧、停留时间）必须设备无关**：若同一模型在不同设备自动取不同阈值，同一现场的告警结论会因设备而异，违背巡检一致性；
- **真正的阈值自动推导依赖校准数据**（标注集 + 精度曲线，对应 `calibration/`），不是按设备型号查表，属另一量级工作；
- 性能类参数（最大检测数、抽帧频率、视频帧率、内存预算）的设备自适应如将来要做，应放在 **App 侧消费层**按设备档位调整，且**不改变服务端下发的业务阈值**。本方案与 App 侧《相机帧、方向与告警短视频本地留存统一改造方案》对齐：App 的设备自适应（如有）只作用于性能参数，服务端业务阈值 App 只读照用。

## 5. 验收标准

- 默认进入参数档案，用户可见字段数显著少于当前（仅业务基线层）；
- 不展开高级区即可完成常规模型的保存与发布，提交值与展开前一致；
- 展开高级区可设置并保存 IoU / maxDetections / 连续帧 / 停留 / 冷却 / 拍照相机分别覆盖；
- 现有校验全部保持：事件编码格式、名称非空、告警置信度不低于检测置信度；
- 保存 / 重置 / 发布的草稿与 CAS 行为、审计记录、下发 JSON 结构与改造前完全一致（协议零变化）；
- App 端读取发布参数的行为不变（`platform` 来源、回退逻辑不受影响）。

## 6. 影响面与定级

| 文件 | 改动 | 定级 |
|---|---|---|
| `admin-web/src/features/models/ParametersDialog.vue` | 字段分层展示、高级折叠、通用告警置信度入口 | L1（纯界面；若前移部分校验则 L2） |
| `admin-web/src/features/models/ParameterReadOnly.vue` | 只读视图同步分层展示 | L1 |
| `admin-web/src/features/models/types.ts` | 若需区分“通用/分别覆盖”的前端视图模型 | L1 |
| 服务端 `app/model_parameters.py` | 不改（协议与默认值不变） | — |
| 下发 JSON / 发布 / CAS / 审计 / 数据库 | 不改 | — |

定级为界面改造：`admin-web` 前端 `npm run typecheck` / `npm run test` / `npm run build` 通过即可，不涉及服务端迁移或协议回归。若评审认为“分别覆盖”的视图模型需要动到提交结构，再升为 L2 并补服务端 JSON 往返测试。

## 7. 流程落地

- 本方案属服务端 `server-video-service` 工程，走该工程 `harness/` 流程登记，与 App 侧改造分仓分任务；
- 需求关系：属对现有 [平台统一模型参数](platform-model-parameters.md) 的**界面呈现优化**，不新增参数语义，建议评审结论为 `clarification`（在现有参数需求正文补“分层展示”一条），不新增 PR；
- 本文为设计评审稿，不单独登记任务、不改协议、不改代码。
