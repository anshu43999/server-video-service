# ADR-001：服务端视频输出协议分阶段选型

状态：**superseded（已被取代，不再生效）**
日期：2026-09-02
取代者：[`docs/adr-002-production-transport.md`](adr-002-production-transport.md)（2026-09-03，任务 `M07-T02`）

> **本文件只作为历史记录保留，不得作为实现依据。**
>
> ADR-001 把 MJPEG / WebSocket JPEG 定为 MVP 与 P1 的输出协议、把 WebRTC 留到 P2 做 PoC。这条路线已被 ADR-002 整体推翻，原因见 ADR-002 的「为什么 ADR-001 的路线是错的」：MJPEG 带宽随观看人数线性放大（720p25 约 15–25 Mbps/人，H.264 约 2–3 Mbps/人），而"一路流多人观看"正是本项目的核心场景；叠加烧进画面丢掉了结构化检测结果；端侧自研 RTSP/H.264 解码把风险压在最难验证的一端；缺少分发层。
>
> 当前生效的决策：**WebRTC/WHEP 为唯一生产播放路径，LL-HLS 为过渡与回退，RTSP 仅供诊断，MJPEG / WebSocket JPEG 降级为测试与诊断通道。** 下文的决策、理由、影响和解冻条件均已作废。

## 背景

服务需要把服务器处理后的画面实时返回移动端。当前主要目标是验证服务端接收、YOLO 开关、叠加和会话控制，而不是立即建设公网直播平台。

## 决策

1. MVP 和 P1 联调继续提供 MJPEG 与 WebSocket JPEG；
2. 上层 REST/会话/YOLO 契约与传输协议解耦；
3. P2 生产协议优先开展 WebRTC PoC，同时保留 SRT 作为专用链路备选；
4. 在目标 Android 设备和真实网络压测完成前，不删除 MJPEG/WebSocket，也不把 WebRTC/SRT 标记为生产已验证。

## 理由

- 当前 MJPEG/WebSocket 已有自动化测试、管理页面和联调工具；
- WebRTC 更接近移动端低延迟播放目标，但需要信令、ICE、连接生命周期和媒体服务器能力；
- SRT 适合可靠低延迟媒体传输，但 Android 播放端集成和解码链路需要额外验证；
- 分阶段可以先交付可观察的业务闭环，再用实测数据决定生产协议。

## 影响

- P1 的带宽效率不是最终生产水平；
- 需要保留输出适配器边界，不能让业务代码直接依赖 MJPEG；
- 发布前必须补充目标 Android 播放器和弱网证据。

## 解冻条件（已作废）

原条件为"完成 `M04-T02` 的生产低延迟输出 PoC，并满足 `docs/transport-comparison.md` 的验证门禁"。该条件不再适用：ADR-002 已直接把生产协议定为 WebRTC/WHEP，不再走"先 MJPEG 再 PoC"的解冻流程，`M04-T02`（原生产低延迟输出适配器）已按 `supersede` 流程终止，替代任务为 `M08-T03`；M04 中的容量压测与故障恢复任务不作废，改为依赖新的编码与分发任务（见 `M07-T04` 与 M08）。本文件不再有解冻路径；如需重新评估输出协议，另开新 ADR。
